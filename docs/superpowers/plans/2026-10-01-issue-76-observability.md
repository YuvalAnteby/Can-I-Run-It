# Issue 76: Budget-conscious observability Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Correlate production API requests, check stages and provider/database dependencies in Azure without logging sensitive data or multiplying ingestion costs.

**Architecture:** Continue using Nest's `Logger`, with a small `ConsoleLogger` subclass, Node `AsyncLocalStorage`, and request middleware. Initialize the Azure Monitor OpenTelemetry distro before importing application modules; export traces/metrics through Application Insights and collect application logs once through Container Apps stdout. Add opt-in monitoring Terraform alongside the existing Container App resource.

**Tech Stack:** NestJS 11, Node 24, Azure Monitor OpenTelemetry JavaScript, the OpenTelemetry API, PostgreSQL instrumentation, AzureRM 4.25.0.

**Spec:** [GitHub issue #76](https://github.com/YuvalAnteby/Can-I-Run-It/issues/76), as expanded by the authorized user task and the decisions below. Baseline: `b4da6ee6` on staging.

## Global Constraints

- Ponytail full: native Nest logging and Node context; no Pino/Winston, collector, dashboard frontend, new logging service/module hierarchy, or speculative provider adapters.
- Keep existing API bodies, status codes, quotas, coalescing, fallback and cache failure behavior. Register middleware before guards and validation.
- Never emit API keys, credentials, connection strings, SQL/parameters, prompts/responses, authorization/cookie headers, request bodies, raw URLs/query strings, IP addresses, or raw exceptions/stacks.
- All metrics use bounded method/route/status/provider/event dimensions; never request IDs, game/hardware identifiers, arbitrary URLs or exception text as dimensions.
- Default logs `info`; Azure exporting disabled unless explicitly enabled, sampling 10%, Live Metrics off. Local startup without Azure credentials works.
- No Terraform apply, deployment, commits, pushes or sending notifications during implementation. User-selected Luna max implementation and independent test author are already authorized; no additional design approval gate.

## Review Focus

- Parallel async requests must keep distinct IDs; invalid, repeated, oversized or multiline ingress IDs must never be reflected.
- Guard rejection, failed DTO validation, missing route, thrown errors and client disconnects must produce one completion record with bounded route labels.
- RAWG embeds its key in the URL; database and auto-instrumentation exceptions may contain secrets even when app log calls are safe.
- Coalesced requests and late provider settlement after a timeout must not duplicate actual call/timeout/failure counters or change permit lifetimes.
- Successful health probes are frequent and must not generate routine logs, inbound spans or PostgreSQL probe spans; failures remain operationally visible.

## Existing flow and boundaries

`POST /api/v1/check` and `POST /api/v2/check/pending/:gameId` route through `CheckRateLimitGuard` into `CheckService`. Both load game/CPU/GPU, look up cached performance, use `GeminiService.estimate`, persist Gemini results when available, otherwise return a heuristic. RAWG runs on discovery/selection routes through `GamesService` and `RawgClient`, not inside `/api/v1/check`; do not invent a RAWG call there. Both providers already coalesce calls and bound permits/timeouts. `AbuseProtectionService.recordEvent` is the existing shared source for failures/timeouts/rejections.

Terraform currently manages only one existing Container App, at one replica, and references an externally managed Container Apps environment. It does not manage that environment, its log destination, workspace, alert contacts or App Insights. Keep that ownership boundary explicit.

### Task 1: Correlated safe backend telemetry

**Interfaces (frozen for the independent test author):**

- `request-context.ts`: `requestContext: AsyncLocalStorage<{ requestId: string }>`; `getRequestId(value: unknown): string`; `requestContextMiddleware(req: Request, res: Response, next: NextFunction): void`. Accept exactly one string matching `/^[A-Za-z0-9._-]{1,64}$/`; everything else gets `randomUUID()`. Response header is `X-Request-ID`. Accepting caller IDs does not confer trust or change authorization.
- `observability.logger.ts`: `ObservabilityLogger extends ConsoleLogger`; constructor `(environment = process.env.NODE_ENV ?? 'development', level = process.env.LOG_LEVEL ?? 'info')`. Preserve all Nest logging methods through the built-in class. Production writes exactly one valid JSON line per message to stdout, including errors. Development keeps readable Nest output. Enabled levels derive from the validated `debug|info|warn|error` threshold; never globally turn on debug by default.
- JSON envelope: `timestamp`, `service: 'ciri-backend'`, `environment`, `level`, `event`, `context`; allowed optional fields: `requestId`, `traceId`, `spanId`, `route`, `method`, `statusCode`, `durationMs`, `provider`, `stage`, `outcome`, `count`, `errorType`. Use `new Logger(Class.name)` at existing call sites and pass structured event objects as the first message argument (Nest 11 has no Nest 12 flattened params). Unknown object keys and Error message/stack are dropped; production free-text strings should be omitted or safely bounded/redacted, never stringify arbitrary objects. No raw error argument in cache/startup logs.
- `telemetry.ts`: `observeStage<T>(stage: StageName, operation: () => T | Promise<T>): Promise<T>`; `observeProvider<T>(provider: 'gemini' | 'rawg', operation: () => Promise<T>): Promise<T>`; `recordTelemetryEvent(event: AbuseEvent): void`. StageName is `check.inputs | check.db_lookup | check.gemini | check.fallback | check.persistence | rawg.search | rawg.detail | rawg.persistence`. Both wrappers preserve returns/errors, close spans in `finally`, log one bounded stage result with duration, and never record raw exceptions. Provider spans use `SpanKind.CLIENT`; stage spans use `INTERNAL`; returning null from a provider means unavailable, not successful dependency. Additional internal helpers are implementation details.
- `telemetry-bootstrap.ts`: `readObservabilityConfig(env: NodeJS.ProcessEnv): { enabled: boolean; connectionString?: string; samplingRatio: number }`; `initializeTelemetry(env = process.env): void`; `sanitizeSpan(span: ReadableSpan): void`. Read `TELEMETRY_ENABLED` (only `true|false`, default false), `APPLICATIONINSIGHTS_CONNECTION_STRING` (trimmed), `OTEL_TRACES_SAMPLER_ARG` (finite decimal 0..1, default 0.1). Reject enabled without a connection string and malformed settings using messages naming only the setting. Validate `LOG_LEVEL` even when exporting is disabled. Call initialization as the first main import, before Nest/AppModule/pg/provider modules. Make repeated initialization harmless; do not register multiple SDK providers.

**SDK decisions:** Use `@azure/monitor-opentelemetry` with directly imported compatible OTel API/resources/trace types packages. Match versions to the distro's peer/dependency constraints and lock them through npm. The current package is CommonJS under NodeNext (no `type: module`); verify emitted `dist/main.js` import order, without adding an ESM loader unnecessarily. Configure service resource `service.name=ciri-backend`, environment attribute, and revision/replica instance when available. Explicitly choose fixed percentage sampling (`tracesPerSecond: 0`, ratio .1; environment sampler `microsoft.fixed_percentage`) so newer default rate limiting cannot override the configured ratio. Enable HTTP inbound and PostgreSQL; disable HTTP outgoing auto collection (manual provider CLIENT spans cover the actual fetch flows), unused database/Azure SDK instrumentations, Console/Bunyan/Winston capture, browser injection, Live Metrics, extra performance counters and offline file storage. Use only application custom low-cardinality metrics; avoid duplicating built-in HTTP metrics if the distro can disable them.

**Sanitization:** Custom span processor applies before export. Keep only bounded safe HTTP method/route/status, database system/operation, service fields, stage/provider/outcome, and request correlation attributes. Remove URL/query/header/body/SQL/statement/parameter/credential attributes, exception events, and `status.message`; sanitize generated span names too. On middleware finish, update root HTTP span name/route using matched Express template (`baseUrl + route.path`), or `unmatched`; never fall back to a request URL. Carry `requestId` as a trace attribute; do not use it as an OTel metric dimension. Configure pg without enhanced statement/parameter reporting; exporter sanitizer still strips default statements.

**Completion and probe rules:** Middleware enters ALS before `next`, sets the response header, and logs `http.request.completed` on finish or premature close exactly once. Add traceId/spanId from active OTel context when present, including unsampled trace IDs. Measure monotonic duration; statusCode is the actual response code, disconnected requests use bounded outcome `aborted`. Record request count/errors/duration for non-probe requests; errors means 5xx. Successful `/api/health/live`, `/ready`, `/postgres` do not log completion or export spans. Ignore probe ingress in HTTP instrumentation and require pg parent span (`requireParentSpan`) so excluded readiness probes do not create root SQL spans. Failed health completion logs stay visible for alerts. Expose `X-Request-ID` in CORS without changing origins.

**Metrics:** meter `ciri-backend`; counters `ciri.http.requests`, `ciri.http.errors`, `ciri.provider.calls`, `ciri.provider.failures`, `ciri.provider.timeouts`, `ciri.rate_limit.rejections`, `ciri.provider.rejections`; histogram `ciri.http.duration` in milliseconds. Provider call increments once after existing permit acquisition/deduplication, immediately before the underlying attempted call. `recordTelemetryEvent` maps existing failure/timeout/ip/global/budget/concurrency events exactly once; call it on every `AbuseProtectionService.recordEvent`, while retaining current aggregated warning rate. Provider rejections use provider+reason, rate-limit rejections use scope. Do not count coalesced waiters as calls. Existing warnings become `{event, count}` structured objects. Do not emit another failure for the same timeout.

### Task 2: Conservative Azure configuration and operational evidence

**Interfaces:** `observability_enabled: bool = false`; `observability_location: string = ''` (required only when enabled); `observability_daily_cap_gb: number = 0.1` (positive); `observability_retention_days: number = 30` (supported workspace values); `observability_sampling_ratio: number = 0.1` (0..1); `observability_action_group_ids: list(string) = []` (existing notification groups). Outputs: nullable workspace/App Insights IDs and a sensitive connection-string output. Keep monitoring-generated env/secret keys reserved while enabled, using existing conflict validations to prevent duplicate names.

When enabled, create a dedicated `PerGB2018` workspace (`${container_app_name}-logs`) and workspace-based App Insights (`${container_app_name}-insights`, web). Apply workspace retention 30 days and .1 GB/day cap; also App Insights .1 GB/day cap, retention 30 and service sampling 100% (sampling occurs once in SDK). Add connection string through the existing Container App secret pattern, and explicit runtime `TELEMETRY_ENABLED=true`, `LOG_LEVEL=info`, `OTEL_SERVICE_NAME=ciri-backend`, fixed sampler and ratio. Disabled preserves current Terraform requirements/runtime and creates no new monitoring resources.

Environment-level diagnostic setting targets `container_app_environment_id` and sends only `ContainerAppConsoleLogs` and `ContainerAppSystemLogs` to this workspace, using resource-specific tables. Do not export `AllMetrics` or ingress HTTP logs to Log Analytics; Azure already retains platform `Requests`, `Replicas`, `RestartCount`, CPU and memory metrics. The externally managed environment must have logs destination `azure-monitor` beforehand. Document the exact CLI command to select that destination and inspect/remove duplicate routing; this implementation must not change the environment or apply infrastructure. An environment-level setting collects other apps too; state that budget limitation, and do not claim per-app filtering.

**Alerts:** Three paid rules maximum, enabled with monitoring, each scoped to this app, using supplied existing action groups; empty list means visible alerts with no external notifications. No inactivity/no-data rule. Use Azure metric alert for `Replicas` average `<1` over 5 minutes, evaluated each minute, severity 1 (min replicas is already 1). Use two scheduled query alerts at 5-minute evaluation/15-minute lookback, severity 2, automatic resolution: (1) unsampled completion JSON has >=5 5xx and >=20% error rate in at least two 5-minute buckets; exclude health routes; (2) at least three unhealthy/crash/backoff system events spread across at least two 5-minute buckets OR failed readiness completions in at least two such buckets. System logs use documented `Reason`/`Log` fields, app scope, and bounded `Unhealthy`/`ContainerCrashing`/`BackOff` conditions; document deployment checks for actual platform reason strings. Native restart metric is diagnostic evidence; do not alert on a permanently accumulated restart count or normal replica creation during releases. Use row-returning KQL with `Count > 0`, one failing period; sustained logic belongs in the query so no missing timestamp multi-period ambiguity.
